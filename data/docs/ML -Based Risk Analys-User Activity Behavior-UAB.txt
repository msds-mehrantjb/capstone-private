# Implementing “User Activity Behavior” as a New Vulnerability in a NIST SP 800-30 Risk Analysis Model

## 1. Purpose

This design defines how to use NIST SP 800-30 style risk analysis to introduce a new vulnerability category called **User Activity Behavior** into your system.

The goal is to make user behavior a measurable risk factor that can be used in likelihood analysis, impact analysis, and final risk scoring.

---

## 2. NIST SP 800-30 Alignment

NIST SP 800-30 risk assessment is based on identifying:

- assets
- threat sources
- vulnerabilities
- predisposing conditions
- likelihood
- impact
- risk

In this model, **User Activity Behavior** should be treated as both:

- a **vulnerability**, because unsafe or abnormal user activity creates exploitable weakness
- a **predisposing condition**, because it increases the chance that a threat event will succeed

This means user behavior should not be treated as just a log record or telemetry field. It should be modeled as a risk input that affects the likelihood of compromise.

---

## 3. Proposed New Vulnerability Definition

### Vulnerability Name
User Activity Behavior

### Definition
A vulnerability arising from abnormal, inconsistent, suspicious, risky, or policy-violating user actions observed on an endpoint, workstation, or server, where those actions increase the probability of unauthorized access, misuse, insider abuse, credential compromise, or operational disruption.

### Why this is useful
Traditional vulnerability analysis focuses on:
- software flaws
- missing patches
- open ports
- insecure configurations

But many real attacks begin through:
- repeated failed logins
- unusual login times
- abnormal session duration
- irregular access frequency
- excessive password resets
- access to unusual files or systems
- privilege use inconsistent with the user’s baseline

This new vulnerability lets you capture those risks formally.

---

## 4. Recommended Risk Modeling Position

You should model User Activity Behavior as a measurable vulnerability object attached to each user-associated asset.

For example:
- workstation assets such as WS-01 should have strong user behavior monitoring
- servers can also include administrator behavior monitoring
- domain controllers can track privileged user behavior
- shared systems can track multiple behavior profiles

This means the vulnerability is not simply “present” or “absent.”
Instead, it has:
- features
- a calculated score
- a likelihood contribution
- mapped threats
- mapped controls
- historical trend

## 5. Behavioral Indicators

I identified a strong starting set of indicators:

- failedLoginAttempts
- accessFrequency
- loginConsistency
- passwordResets
- sessionDuration

---

## 6. What Each Indicator Means

### failedLoginAttempts
High values may indicate:
- brute-force activity
- credential stuffing
- forgotten password
- suspicious account use

### accessFrequency
Measures how often the user accesses systems, files, or services.
Risk increases when activity deviates sharply from normal baseline.

### loginConsistency
Measures how stable the user’s logon pattern is over time.
Low consistency may indicate shared credentials, misuse, or attacker activity.

### passwordResets
Frequent resets may suggest:
- account takeover attempts
- poor password hygiene
- abuse of identity processes

### sessionDuration
Sessions much longer or shorter than baseline may indicate:
- unattended sessions
- automated misuse
- lateral movement preparation

## 7. Implementation 

You should implement this in five stages:

### Stage 1 — Collect user behavior telemetry
Install or deploy a local agent on WS-01 or other endpoints that gathers behavioral signals daily.

### Stage 2 — Build feature summaries
Convert raw logs into normalized daily behavior features.

### Stage 3 — Compute a User Activity Behavior score
Calculate a weighted score or anomaly score.

### Stage 4 — Map score to likelihood
Translate the score into NIST-style likelihood categories.

### Stage 5 — Combine with CIA impact
Use your existing CIA asset ratings to compute final risk.

## 10. How to Compute the Behavior Risk Score

A weighted scoring method is the best first implementation because it is simple, explainable, and auditor-friendly.

### Suggested formula

BehaviorRiskScore =
(0.15 × failedLoginScore) +
(0.30 × accessAnomalyScore) +
(0.10 × loginVarianceScore) +
(0.20 × passwordResetScore) +
(0.25 × sessionAnomalyScore) 

### Why weighted scoring is good
- easy to explain in your report
- easy to audit
- easy to tune
- no black-box dependency
- can later be replaced or supported by ML

Start with weighted scoring first.
Then add an ML anomaly score as a second parallel signal.

---

## 11. ML-Based Scoring

Use ML to generate the behavior score.

### Good model choices
- Isolation Forest
- One-Class SVM
- Local Outlier Factor
- Autoencoder
- LSTM for sequence patterns

### Practical implementation
Use this two-layer model:

#### Layer 1
Rule-based weighted score

#### Layer 2
ML anomaly score

Then combine them:

FinalBehaviorScore =
(0.60 × WeightedRuleScore) +
(0.40 × MLAnomalyScore)

This gives you:
- explainability
- adaptability
- better detection quality

## 12. Mapping Behavior Score to NIST Likelihood

Translate the numeric score into likelihood categories.

### Suggested mapping
- 0.00 to 0.20 = Very Low
- 0.21 to 0.40 = Low
- 0.41 to 0.60 = Moderate
- 0.61 to 0.80 = High
- 0.81 to 1.00 = Very High

### Why this matters
In NIST SP 800-30, risk is not just a raw number.
You need understandable categories for decision-making and treatment.

So the user behavior model should produce both:
- numeric score
- verbal likelihood category

---

## 13. Impact Analysis Using CIA

You already have CIA impact ratings in your system.
That means the behavior model should affect likelihood, while the asset profile affects impact.

### Example
A suspicious behavior score on a low-value kiosk should not be treated the same as suspicious behavior on:
- domain controller
- HR workstation
- payroll server
- administrative laptop

### Suggested CIA mapping
Convert CIA ratings into a numeric impact score.

Example:
- Low = 1
- Medium = 2
- High = 3
- Very High = 4

Then compute an overall impact value using the highest CIA dimension or a weighted CIA formula.

### Example impact method
ImpactScore = max(confidentiality, integrity, availability)

This fits your existing “maximum impact resolution” thinking.

---

## 14. Final Risk Computation

After deriving:
- behavior-based likelihood
- asset-based impact

compute the final risk.

### Suggested formula
RiskScore = LikelihoodScore × ImpactScore

### Example scale
LikelihoodScore:
- Very Low = 1
- Low = 2
- Moderate = 3
- High = 4
- Very High = 5

ImpactScore:
- Low = 1
- Medium = 2
- High = 3
- Very High = 4

### Example
WS-01 has:
- behavior likelihood = High = 4
- impact = Medium = 2

RiskScore = 4 × 2 = 8

Then map final risk:
- 1 to 3 = Low
- 4 to 6 = Medium
- 8 to 12 = High
- 15 to 20 = Very High

## 17. Recommended Classification Logic

Define User Activity Behavior vulnerability status as one of these:

- Not Observed
- Low Concern
- Moderate Concern
- High Concern
- Critical Concern

### Suggested logic
- 0.00 to 0.20 = Not Observed
- 0.21 to 0.40 = Low Concern
- 0.41 to 0.60 = Moderate Concern
- 0.61 to 0.80 = High Concern
- 0.81 to 1.00 = Critical Concern

This gives you a vulnerability classification that is separate from overall risk.

That is useful because:
- vulnerability severity and risk are not always the same
- high behavior concern on low-impact asset may still be moderate overall risk
- moderate behavior concern on very high-value server may still be high overall risk
